# Connected life and anticipatory assistance

September 14, 2026. User-directed architecture and bounded first implementation. Release validation is recorded in [overnight-build.md](overnight-build.md).

## Current implementation and limits

The current source provides a trusted host connector registry, private connection/evidence storage, an encrypted credential vault, Google loopback OAuth, Google Calendar/Gmail/Plaid read adapters, durable research jobs, evidence-linked inferred memories, private preparation plans, guarded appointment reminders and bounded inferred weekly routines. Account connection automatically starts the workflow after provider identity and scope checks. Observe and Prepare are standing choices; the user does not need to restate an evidence-supported appointment as a chat command. The existing boards show preparation reasons, and Settings exposes connection state and controls.

Research currently means deterministic calendar, communication and spending specialist checks. These jobs do not invoke an LLM, browse external sources or run on remote devices. Hourly sync and daily maintenance revisit four planning horizons; this is not a complete plan spanning every day of several months. The scope is deliberately concrete:

- Google Calendar and Gmail require a registered Google desktop OAuth client configured on the host and the user's provider authorization. This development work connected no real accounts. Calendar reads the primary calendar; Gmail reads a bounded message window and metadata, including available snippets.
- Plaid reads host-provisioned transaction access. Consumer Plaid Link onboarding is not implemented. Transaction patterns do not establish current balances, income, reserves, complete financial coverage or a dependable cash-flow forecast.
- Appointment evidence can create a private checklist and, when a suitable future reminder time exists, a one-time reminder. Delivery rechecks source access, Prepare mode, expiry, user edits, quiet hours and proactive settings. Quiet-hour suppression skips that occurrence; it does not defer a notification burst. A saved plan or delivered reminder does not mean the appointment or checklist steps are complete.
- Consistent historical self-organized events can support a tentative weekly-habit memory and a guarded weekly routine under Prepare. The rule requires matching titles, at least three consecutive weekly local dates and exact local weekday/time, suppresses a routine when a matching future calendar booking already exists, and expires it within ninety days of its latest supporting event. This is a narrow inference rule rather than general habit understanding. No provider in this slice supplies authoritative receipts for automatic checklist-step completion.
- Analysis is currently scoped to one personal connection at a time. Cross-account joined planning, weather/news/event research, shopping carts, purchases, messages/calls and vehicle/home controls are not implemented. The broader named provider catalog is a direction, not a list of working account connections.
- Additional trusted host adapters can register through the typed plugin API. There is no remote plugin installer, arbitrary-code sandbox, shared household account projection, distributed research transport, automatic stronger-model selection or pooled device memory.

Provider evidence and cursor checkpoints, research tasks, private preparations and reset state are durable. Tests use synthetic account transports and isolated stores; provider enrollment, real-account onboarding and production coverage must be established separately. The remaining sections describe the authority boundaries and extension contracts, including capabilities beyond this first slice.

## Product behavior

Connecting an account should start useful background analysis. Ellie notices commitments, recurring patterns, possible needs and opportunities, then prepares private plans, reminders and widgets within the standing choices made during connection. The user should not need to issue commands that restate what available evidence already establishes. Conversation remains a direct way to correct Ellie, inspect a reason, change a preference or request something new.

For example, sufficiently consistent calendar history can suggest a morning scheduling preference; a confirmed upcoming appointment can create a preparation checklist; communication history can suggest a timely follow-up; repeated payments can identify a recurring expense worth reviewing. A supported completion receipt can update an existing step. These are different conclusions with different evidence requirements. A message about completing a form is not proof it was submitted, and the passage of an appointment time is not proof the appointment happened.

The existing boards, widget grid, expanded apps and floating orb stay intact. Connections and standing choices are secondary controls. Timely preparations appear in the ordinary dashboard, with a short reason and accessible evidence references.

The broader connector direction includes Google Calendar, Gmail, shopping accounts, messaging and calls, Discord, Slack, financial accounts, Tesla, home devices, Spotify, YouTube and Apple services. This is a product direction, not a claim that every named service offers an equivalent account API or that Ellie already supports it. The first provider slice covers Google Calendar, Gmail and Plaid read adapters. Provider registration, required access scopes and onboarding availability must be verified against each provider's official documentation.

## Boundaries and ownership

The trusted connector broker is separate from generated browser widgets. An iframe can receive a narrowly projected view or invoke an explicitly granted typed operation. It never receives OAuth tokens, refresh tokens, vault keys, arbitrary network access or the connector store.

The host extension API is `ConnectorPluginRegistry` in `packages/life-plugins/src/connectors.ts`. A trusted server registers an already instantiated adapter together with a version-one connector manifest containing ID, label, observation kinds, authentication family, requested scopes and fixed HTTPS origins. Registration rejects unknown fields, credential/executable declarations, duplicate IDs, adapter-ID mismatch and private or noncanonical origin literals. Adapter results must stay within declared observation kinds. Metadata projections and registered method references cannot be changed by mutating returned arrays.

This registry does not install remote modules, run downloaded code, delegate host capabilities to generated HTML or provide a sandbox for arbitrary third-party JavaScript. Origin declarations do not independently inspect DNS resolution or constrain malicious code already trusted by the host; each adapter must retain its own bounded fixed-origin network policy. Generated widget manifests continue using the separate storage/data projection API. Connecting an account and publishing a widget are different operations with different authority.

| Component              | Responsibility                                                                                                                                                             |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Provider adapters      | Fixed-origin authenticated API calls, normalized observations, incremental pagination, tombstones and typed failures. Credentials and fetch are injected by the host.      |
| Connector broker/store | Personal account ownership, connection state, standing grants, encrypted credential references, durable evidence, cursor commits, revocation generations and bounded jobs. |
| Anticipation analysis  | Pure analysis of normalized observations and explicit settings into evidence-linked inferences and proposals. No network, store mutations or synthetic chat commands.      |
| Research runtime       | Bounded account analysis and horizon jobs using the task runtime, cancellation and admission budgets.                                                                      |
| Trusted executor       | Recheck grant, evidence freshness and connection generations, apply eligible private preparations, and record actual completion receipts.                                  |
| Dashboard/orb          | Show resulting preparations, concise reasons, connection state, exceptions and corrections.                                                                                |

First-slice connections and account evidence belong to the authenticated person's private scope. A connection does not automatically share mail, purchases, financial activity or inferred preferences with a household. Later sharing needs a separate projection with explicit source and destination authorization.

## Connection and evidence contract

The provider type source is `packages/life-connectors/src/provider-types.ts`. Canonical providers are `google-calendar`, `gmail` and `plaid`. The broker creates the connection ID and binds the account identity returned by the provider; clients cannot assert that an arbitrary account is theirs.

Provider setup availability is separate from connection state. Connection states distinguish `connecting`, `connected`, `paused`, `error` and `revoked`. A connection becomes connected only after a successful provider identity check. The public projection includes provider, account label, state, last successful sync, actionable error category and allowed behavior. Partial sync remains distinguishable from a successful complete sync; a later coverage display must not imply that a bounded provider window covers the entire account. The projection excludes credential references, tokens, private cursors and internal request diagnostics.

`ConnectorObservation` combines a trusted `connectionId` with a provider observation. Every observation has a stable `sourceKey`, a material `sourceRevision`, `observedAt`, a title and a typed payload. Fetch time must not change the material revision or create duplicate evidence.

| Kind          | First normalized fields                                                                                                                                                                       |
| ------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `event`       | Instant start/end or local all-day start/end dates, time zone, confirmed/tentative/cancelled status, optional location and self-organizer information. Preserve exclusive calendar end dates. |
| `message`     | Sent time, literal sender and recipients, subject, optional bounded snippet, labels and incoming/outgoing/unknown direction. Snippets are partial evidence.                                   |
| `transaction` | Posted time, canonical signed `amountDecimal` string, currency, optional merchant/category and pending status. Preserve provider outflow/inflow semantics.                                    |
| `deleted`     | Stable source identity/revision and the previous kind. Deletion retracts source availability; it is not evidence that a task completed.                                                       |

An evidence reference is `{ connectionId, sourceKey, sourceRevision }`. Analysis outputs may refer only to supplied, current, nondeleted observations. The broker verifies those references again before publication or execution. Saved life records retain these references and enough source identity to invalidate derived state on account revocation or source replacement.

Adapters expose identity checking and bounded `pull` operations. A pull accepts host credentials, a stable cursor, an optional continuation, an observation window, an item limit and an abort signal. It returns the verified account ID, observations, an optional next continuation, an optional new stable cursor and a completion flag. The broker commits each page's evidence and continuation together. It advances the stable incremental cursor only after the complete snapshot/batch succeeds. Provider invalid-cursor recovery must be explicit; a partial or failed page cannot establish exhaustive absence.

Initial Google pagination preserves its original query window. Expired Calendar cursors clear local evidence before a full sync, consistent with [Google's synchronization contract](https://developers.google.com/workspace/calendar/api/guides/sync). Plaid pagination restarts from the original committed cursor when the provider reports a changed batch, and an Item whose transactions are not ready remains distinct from a successfully synchronized empty history. These behaviors follow the [Plaid transaction sync contract](https://plaid.com/docs/api/products/transactions/#transactionssync).

Deduplication uses connection, source key and material revision. Replay must not create duplicate plans, reminders or inference records. Error categories distinguish setup/reauthorization, revocation, rate limits, transient provider failure, malformed responses and bounded partial results. Neither errors nor progress messages contain credential values or raw sensitive response bodies.

Money stays decimal data until a supported currency's minor-unit rules permit exact conversion. Plaid positive amounts represent outflows and negative amounts represent inflows. Expense analysis uses settled positive outflows; it skips unknown currencies, unsupported precision and pending transactions. It does not infer income from a balance, transfer, missing period or absence of transactions.

## Authentication and credential lifecycle

Google connection uses a registered client ID supplied by trusted server configuration, native loopback OAuth, PKCE and offline refresh. Unconfigured client registration produces an honest setup-required state. This implementation work does not connect or read real accounts.

On macOS, the trusted host opens the exact Google consent URL in the operating system's default browser through `/usr/bin/open`, with no shell or arbitrary command selection. A bounded launch failure or another platform uses explicit manual-browser guidance. The embedded Ellie view remains available and refreshes connection state; the external callback page tells the user to return to Ellie. Google disallows embedded user agents for this native-app authorization flow, so an in-app webview navigation is not a substitute for the external browser. See [Google's native-app OAuth requirements](https://developers.google.com/identity/protocols/oauth2/native-app#disallowed_useragent).

The start endpoint requires the existing authenticated session and valid local Origin. The server selects provider endpoints and permitted read scopes. A cryptographically random state is one-use, expires within ten minutes and binds actor, provider, requested scopes and exact redirect URI; the PKCE verifier remains host-only. Consume state atomically before exchanging the authorization code. A callback may arrive without the Strict session cookie because state and PKCE bind the initiating authorization, but it must use the exact expected loopback host/path and may not accept actor, provider or redirect authority from query parameters.

The host verifies provider account identity and granted scopes before marking the connection connected. It does not trust an unsigned token payload or a client-supplied account identifier. Diagnostics and confirmation content exclude authorization codes and tokens. Credential file replacement is atomic, and the broker rechecks the connection generation before saving a refreshed credential. The vault and connector database are separate stores, with cleanup/recovery handling between them rather than a claimed cross-database transaction.

The first vault stores encrypted credential records with an installation key protected separately by private file permissions: mode 0700 directory, mode 0600 key/data files, authenticated encryption and atomic durable updates. Credential ciphertext uses a bounded JSON file with atomic replacement; account metadata and evidence use separate SQLite storage. Vault keys and plaintext credentials are excluded from application projections, model prompts and personal exports. This protects the vault under the operating system's file access controls; it does not prevent the host account owner from reading the key. The slice does not modify Keychain or native installer/service behavior.

Plaid initially consumes host-provisioned credential references through the same resolver. Consumer Link onboarding and production provider enrollment remain visible setup dependencies until implemented; an injected test credential is never represented as a connected real account.

## Inference and standing permission

An inference is a hypothesis with a stable key, kind, statement, evidence references, evidence-strength score, caveats and expiry. First kinds are preference, habit, relationship, goal and commitment. Scores describe a rule's evidence strength, not calibrated probabilities. Inferences are stored separately from explicit preferences and can be dismissed, superseded or marked stale. Current explicit settings and user corrections always win.

Connecting and permitting account reads does not itself authorize every possible write. Setup offers a clear standing choice whose scope persists across turns:

| Standing choice        | Eligible behavior                                                                                                                                                                                |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Observe                | Sync permitted sources, derive private hypotheses, explain opportunities and maintain private evidence.                                                                                          |
| Prepare                | Observe plus bounded private checklists, internal reminders, plans and dashboard notices grounded in current evidence. Ordinary eligible actions do not need a repeated command or confirmation. |
| Specific external rule | A later typed rule for a particular external action family, account, recipients/resources, limits, expiry and exclusions. Execute only when the concrete action fits that rule.                  |

The first executor supports private preparation. Sending messages, purchases, bookings, financial transfers and vehicle/home control are separate typed capabilities. A matching explicit standing rule or concrete authorization is required before such an action runs. Account content, inferred habits, a high confidence score and another agent's output cannot create a permission grant.

Autonomous work enters a trusted anticipation API with actor, source connections, horizon and captured grant/evidence revisions. It must not fabricate a user prompt to pass the chat command parser. Immediately before committing, the host checks current source access, standing grant, exclusions, quiet hours, proposal expiry, dedupe key and all referenced source revisions. A changed prerequisite suppresses or regenerates the proposal.

An internal saved plan is complete as a save operation only after durable storage succeeds. Its individual steps remain unfinished until supported completion evidence or a user correction establishes otherwise. External actions later need provider receipts and, where supported, readback. Queued, accepted, completed, failed and unknown outcomes remain distinct. Retries use operation idempotency keys; ambiguous external outcomes cannot be blindly replayed.

## First analysis rules and workers

The pure `analyzeLife` function consumes normalized observations, explicit settings, dismissed keys, current time, time zone and requested horizons. It returns bounded inferences and anticipatory proposals. Initial limits are 32 inferences, 12 proposals and eight evidence references per result. Deterministic result keys exclude retrieval timestamps.

- A confirmed upcoming appointment can produce a preparation checklist and an eligible reminder. Titles and timing come from the actual event; no diagnosis or completion is inferred.
- At least three self-relevant confirmed appointments on distinct local dates can support a tentative morning scheduling preference. This does not rewrite explicit scheduling settings.
- At least three consecutive weeks of self-organized events at a matching local weekday/time can support a bounded weekly routine. Monthly events that happen to share a weekday do not qualify, and an existing future booking suppresses duplicate scheduling.
- At least three outgoing messages to the same literal address can support a communication cadence and a later follow-up proposal. An address or display name alone does not prove that person's family relationship. A follow-up proposal does not send a message.
- At least three supported settled merchant payments over distinct periods can support a recurring-expense review. Repeated payments alone do not prove a subscription, contractual obligation or income source.

Each proposal includes kind, title, reason, evidence references, evidence strength, expiry, horizon, short steps and an optional suggested reminder time. First proposal kinds are event preparation, follow-up, recurring-expense review and horizon planning. Missing coverage and ambiguous identity/timing remain visible caveats rather than invented facts.

Account connection starts an initial bounded sync and analysis workflow. The first runtime persists hourly sync and daily 06:00 local-time analysis templates. Each completed sync and daily analysis maintains the day, month, quarter and year planning windows together. These are analysis horizons, not four separately implemented calendar-period schedulers. Refresh requests coalesce by account, authorization/context revision and minute, so a changed standing choice takes effect promptly. Missed intervals coalesce to current work rather than replaying a notification burst. Event-driven provider subscriptions and distinct monthly/quarterly/annual review schedules remain later integrations.

Parallel workers receive only the relevant evidence slice and inherit the parent's limits and permissions. Three initial workers independently analyze calendar, communication and spending evidence across the requested horizons; one dependent publication job combines and rechecks all outputs. Deterministic matching handles supported patterns without paying for an LLM call on every refresh. Exported persona prompts describe future model roles; they are not evidence that LLM research has run. Later model-based research must return the same evidence-linked contracts and pass the same authority gate.

The `createConnectedResearch` host API injects `tasks`, `snapshot(actorId, connectionId)`, `sync(actorId, connectionId, signal)` and `publish(actorId, connectionId, generation, result, signal, contextRevision)`. Snapshots contain current normalized evidence, explicit settings, dismissed keys, time zone, standing mode, an authorization generation and an optional context revision. The broker supplies the context revision and synchronously rechecks it at publication; it covers contrary new evidence and corrections in addition to the exact supporting references. Methods are `connectionAdded`, `refresh`, `revoke` and `close`.

Persisted task inputs contain actor/connection references, generation, context revision and persona identity rather than copied account activity. Task owners are the authenticated person. Sync and publication require `life.connections.read` and `life.connections.write`; specialist analysis requires read capability. Each initial tree normally has five tasks and allows nine to recover one interrupted stale batch. Two jobs per tree may run concurrently, each with a sixty-second execution budget and at most two attempts. Revocation cancels all descendants of the account's deterministic initial/hourly/daily roots. Shutdown aborts and drains actual callbacks before stores close; deleting task rows alone is not proof that callbacks stopped.

Device capacity is advisory until a trusted worker transport exposes authenticated availability. More eligible devices can run independent work or offer a stronger model that fits one eligible device. Their memory is not automatically pooled. Worker selection respects per-device memory, model availability, foreground load, data-disclosure rules, locality and heartbeat freshness. A device appearing does not silently enable cloud processing or expose private account evidence to it.

## Revocation, reset and verification

Revoking an account first advances its generation and blocks new work, aborts active sync/research, cancels account-bound tasks and deletes its credential reference. Late refreshes and analysis results fail the generation check. Source-derived inferences and untouched automatic preparations become stale or are withdrawn; explicit user edits remain distinguishable. Deleting source evidence must not recreate it through retained model history or an old cursor.

Personal export includes inspectable connection metadata, evidence references, inferred records, standing choices and action receipts, with sensitive content under the existing private export rules. It never exports credentials or OAuth state. Personal reset coordinates task drain, connector state/evidence/vault removal and existing life/plugin deletion through a durable journal. Report completion only after every required store has finished; do not claim a cross-database transaction or deletion from the upstream provider.

Acceptance requires synthetic provider HTTP fixtures plus actual service/UI flows: identity mismatch, redirects, malformed/oversized data, expired state, replayed callback, token rotation, pagination, invalid cursors, tombstones, partial coverage, restart, rate limits, cancellation and revoked-account late results. Analysis checks must include explicit contradictions, misleading message snippets, unknown currencies, source deletion, stable dedupe, future timestamps and incomplete history. The connected vertical slice is accepted only when evidence ingestion causes an appropriate private preparation under a standing grant, survives restart without duplication, explains its sources and stops after revocation/reset. No real user account is required for those tests.
