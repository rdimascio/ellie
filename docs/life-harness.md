# Conversational life harness

`@ellie/life-harness` turns a bounded set of conversational requests into scoped life records, durable tasks, and installed plugins. `createLifeHarness({ store, tasks, plugins, mlb, model?, context?, now? })` returns `chat`, `buildPlugin`, and `revisePlugin`. The HTTP service authenticates `LifeActor` and `LifeScope` before passing them in; the harness asks `LifeStore` to enforce membership again before reading or acting.

The deterministic path works without a model. It supports explicit remembering, correction, forgetting and source search; contacts and birthdays; gift needs with interests and budgets; relative reminders and timers; reminders and appointments anchored to today, tomorrow, or the next named weekday; daily and weekly routines; completion and cancellation; today’s agenda; explicit concise or warm preferences; feedback; built-in arcade and MLB plugins; fresh shopping signals; preparation checks; and bounded background source summaries. Unsupported chat returns concrete examples instead of fabricating a general answer. Direct SDK callers have a bounded process-local history cache. The HTTP service persists actor-private conversations with explicit history, deletion, export and reset controls and supplies only current, bounded completed turns as model context. A conversation in a group context remains private to its author.

`LifeOperations` is the shared validated executor for deterministic and model-translated reminders, events, needs, contacts, and source summaries; it also provides bounded scoped queries to model plans. A model plan can contain at most one mutation. It cannot choose an actor, scope, handler, capability, record identifier, revision, or arbitrary data patch. The dispatcher rechecks exact scope access, validates local time through `@ellie/life-time`, and derives replies from the stored record or queued task result. A model proposal runs only when the current user message directly requests the matching operation family; history, memories, adopted guidance, and source text never authorize a write.

Trusted service callers may supply bounded completed `history` and an `isContextCurrent` callback on `ChatRequest`. The harness prefers this history over its process-local fallback and checks the callback, actor generation, scope generation, and scope access after model work and immediately before modeled effects. These fields are internal integration seams and must not be accepted from an unauthenticated HTTP body.

Birthday input creates linked contact, birthday, open gift need, and preparation reminder records. A reminder is a one-shot task handled by `reminder.notify`. At execution, the handler rechecks record access and current state. Deleted records, revoked group membership, cancelled reminders, and completed linked needs produce a verified skip. Successful delivery creates one idempotent scoped notification event record. The host can then surface that record through its authorized native notification path.

“Work on … in the background” atomically queues up to four parallel `knowledge.summarize-source` children beneath one `knowledge.aggregate` root. The tree has a shared 30-second deadline, concurrency of two, and a read-only capability ceiling. The root runs only after its children and returns a bounded summary plus source IDs, revisions, titles, and references. Without a model it returns a cited extractive summary. It does not claim internet research. Sources are rechecked after model calls and at aggregation; deleted, changed, or newly inaccessible sources are omitted. A service must repeat that check before displaying a saved result because access can change after task completion.

If every selected source becomes unavailable, the verified result contains no citations or source-derived text. It returns the generic summary “No current source passages remain for this summary,” the omitted count, and reason `no_current_sources` so clients can explain the completed workflow without exposing stale content.

`rerunBackgroundSummary({ actor, scope, taskId })` accepts only a terminal `knowledge.aggregate` root in the authenticated scope. It reuses the bounded query, selects current accessible source revisions, and creates a new bounded workflow with a new idempotency tree and deadline. The old root and children remain historical and are never reset or replayed.

`invalidateContext(actor, scope)` clears all bounded in-memory conversation history for that actor and scope. The harness calls it after conversational correction or forgetting. Services call it after successful record, source, or import mutations so removed text cannot survive in a later model prompt.

`invalidateActorContext(actor)` clears personal and group conversation caches for that actor and invalidates their in-flight foreground model replies. It is used during personal reset; it does not delete or modify shared group records.

“Teach Ellie: …” creates and immediately enables a versioned guide in the current scope. “Use &lt;source title&gt; as guidance” is the only path that adopts source text, requires an exact source title and at most 4,000 characters, and pins the source revision. “List guidance”, “Pause guidance &lt;name&gt;”, and “Resume guidance &lt;name&gt;” expose its state. Changed, deleted, or inaccessible source revisions disable the guide. Adopted guidance can shape a model response, while the direct user request has priority and guidance never grants tools or permissions.

Source passages are passed to a model under an `untrustedEvidence` label. Document text is never parsed as commands or permission. The optional model can choose `reply`, `search_sources`, `create_memory`, or an allowlisted `life_operation` in a strictly validated plan. Life operations cover reminder/event/need/contact creation, need completion or cancellation, agenda queries, source summaries and clarification. A model-proposed memory is saved only when the current user message directly asks Ellie to remember it; recall questions and negated requests cannot authorize a write. Operation receipts come from actual stored or queued outcomes, so a later model reply cannot replace them with a conflicting success claim. The harness does not evaluate generated code or expose a general tool executor.

`LocalOpenAIModel` supports an OpenAI-compatible `/chat/completions` endpoint on an unauthenticated literal `127.0.0.1` or `::1` HTTP address only. It rejects hostnames, credentials, remote hosts, redirects, oversized streamed responses, malformed JSON, extra plan fields, and unknown actions. No cloud provider is enabled by this package.

Built-in plugin requests use `builtInManifest`. Other plugin requests require a configured model builder. Generated output is validated and installed as `kind: "custom"` with `capabilities: ["storage"]` only. Its HTML is intended for the plugin host’s sandboxed UI and receives no filesystem, server, native-app, or arbitrary network capability from the harness.

`buildPlugin` and `revisePlugin` accept an optional `AbortSignal` and generation deadline. The deadline defaults to 90 seconds and can be set from 1 millisecond through 120 seconds. A harness admits at most two model-backed plugin generations at once. A timed-out noncooperative builder keeps its admission slot until its underlying promise settles, while its late output can never be installed. The harness checks cancellation, conversation context, actor reset generation, current scope access, and revision state again after generation and immediately before changing `PluginStore`. Built-in generation performs the same preflight checks but does not wait on a model.

Generation failures use `PluginBuildError` with a bounded code: `cancelled`, `timeout`, `invalid_candidate`, `context_changed`, `access_revoked`, `conflict`, or `model_unavailable`. Invalid candidate details and raw generated HTML are not included in the user-facing message. A failed new build writes no plugin. A failed or conflicting revision keeps the prior active version and capability list unchanged. Unexpected persistence errors remain errors from the underlying store so callers do not mistake an uncertain storage outcome for a known candidate rejection.

`revisePlugin` is a bounded extension-improvement loop. A custom plugin revision gives the model the prior sandboxed HTML and the explicit user correction, validates the candidate, and atomically activates it through `PluginStore.update` without adding capabilities. Saved versions support rollback. Built-in code is fixed; deterministic revisions can rename a built-in app. This updates a user-owned extension and is not model training or permission self-modification.

Place-linked reminders store a named store on an open need and wait for an authorized signal. “I’m shopping at …” evaluates one fresh transient shopping observation through `ProactivityEngine`; the harness stores no raw coordinates and does not claim a geofence exists. Preparation checks use upcoming scoped events within 48 hours.

Current parsing is intentionally narrow. Relative timers understand integer minutes, hours, and days. Explicit dates, today/tomorrow/next-weekday times, birthdays, and daily or weekly routines use the active scope’s IANA time-zone setting, falling back to the coordinator zone when none is configured. Invalid clocks, nonexistent DST times, and ambiguous repeated times are rejected instead of shifted or guessed. Annual February 29 birthdays advance to the next real leap-day occurrence. Rich calendar language, external research, email, purchases, persistent location, and native delivery require explicit adapters. Travel-aware scheduling still needs explicit trip-zone handling and calendar adapters.

A direct reminder request without a time returns a trusted `continuation.create` draft and asks when. The service persists one `PendingLifeIntent` for the private conversation; structured pending data is never accepted from the HTTP client. A later bounded answer such as “Tomorrow at 10” returns `continuation.answer` and does not mutate data. After the service atomically merges and claims that answer, `continuePendingIntent` executes the complete reminder through `LifeOperations`. Unrelated chat leaves the request pending, “never mind” returns a cancellation directive, and expired, revoked, ambiguous, or nonexistent local-time answers cannot execute. The awaiting lifetime is controlled by the durable service and is currently 24 hours.

Reminder rescheduling uses a revision-bound target and the task runtime replacement protocol. `LifeOperations.rescheduleReminder` prepares a nondispatchable task, records the new task ID on the reminder with an expected revision, then activates it. Durable journal callbacks mark both boundaries for recovery. `recoverReminderReschedule` activates only when the current scoped reminder still points at the prepared task; otherwise it discards the replacement. The notification handler also verifies that its task or recurring parent is still the reminder’s current task, so an old occurrence produces a verified `task_superseded` skip. Event rescheduling uses an expected record revision and preserves the prior duration unless a validated replacement duration is explicit.
