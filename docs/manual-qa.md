# Ellie manual QA

Updated September 17, 2026. This catalogue preserves earlier sessions and defines future build-specific checks. A session is ready only when the coordinator names the exact build, target and prerequisites; do not infer a current handoff from an older preview record.

## What to open

**Current handoff:** use only the exact app and browser build named by the coordinator for that session. If no build-specific handoff is supplied, report **blocked: candidate handoff**. Do not install another build, change enrollment or repeat permission setup from this document alone.

**Earlier previews:** prior native Mac and Life preview results remain historical evidence. They do not establish which source, model or authenticated session is running now. For a later Life session, the coordinator must supply a fresh authenticated preview and identify its source; if it asks for authentication, report **blocked: preview session** and do not reuse an expired one-time link.

The coordinator supplies a private handoff folder containing this guide, a current `agenda-qa.json` with synthetic events and `invalid-import.json` for rejection checks. Fixture paths, preview authentication links and owner configuration stay outside the repository.

Use a dashboard and records named **Ellie QA** so test data is easy to recognize. Keep existing dashboards and account settings. A missing control is a build/setup mismatch to report, not a reason to reinstall services or certificates.

To repeat them on the execution mini, use its existing checkout and Node identity. Run each command separately, with a normal, non-minimized Arc window, and watch the actual result:

```sh
bun run ellie say "Ellie, open Arc"
```

## Reporting and milestone rules

Every coordinator status update gives the milestone, completed work since the last update, current work across both tasks, blockers, and next action. No invented overall percentage. The coordinator will provide a fresh, build-specific checklist for each milestone and record results against that build.

Use **PASS**, **FAIL**, or **BLOCKED**, with case ID and a short observation. Screenshots are optional; avoid sharing pairing codes, credentials or private transcripts. A concise failure example is `N04 FAIL — note survived, chore reset after relaunch`.

Milestones progress through engineering, automated checks, ready for manual QA, owner QA passed, and accepted candidate. A merge or automated pass does not substitute for owner QA. Failures get a fix and focused retest; independent work can continue while a milestone awaits your result. The coordinator will preserve earlier accepted evidence and will not mark a new build accepted by copying an old result.
