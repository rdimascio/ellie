# Service distribution trust

The packaged service candidate is currently a development artifact. This document defines the public-distribution boundary before Developer ID support is added. It does not certify an artifact or authorize an installed upgrade.

## Authenticate the manifest as well as native code

The current release is a directory containing `SOURCE.txt`, `manifest.json` and `payload`. Its manifest detects changed payload files, but the directory itself does not authenticate the manifest. Checking a helper's signature or identifier alone therefore cannot establish the origin of the TypeScript and other resources that Node will execute.

Public distribution must provide an independently trusted bootstrap installer whose code-signature resource seal covers the exact manifest bytes. The bootstrap verifies that sealed resource before interpreting the candidate release, requires the external manifest to match byte for byte, then verifies every declared payload file, mode and path. `SOURCE.txt` must also match its sealed source record. A changed script with a recomputed external manifest must fail this check.

The authorization bundle must live outside the manifest's payload inventory to avoid a circular signature/hash dependency. The native code is signed first, the final manifest is generated next, and the bootstrap's manifest resource is sealed last. The installed release retains that authorization bundle unchanged so later inspection, selection and launch can revalidate the same authenticated manifest.

The bootstrap's initial trust comes from a trusted distribution channel or an explicitly pinned publisher policy acquired independently of the candidate. Gatekeeper and notarization are additional gates; acceptance by Gatekeeper alone does not identify a download as Ellie. Neither a manifest's Team ID nor a program's self-reported signing identity is a trust root. Apple's [code-signing policy discussion](https://developer.apple.com/library/archive/technotes/tn2206/_index.html) distinguishes signature validity from the policy used to trust it.

## Explicit policy and compatible state

The trusted verifier selects one closed policy before reading release metadata:

- Development policy accepts the existing version-1 development format. It confers no publisher authenticity and remains available for stopped legacy migration.
- Developer ID policy requires an independently pinned Ellie Team ID, fixed component identifiers, the authenticated manifest and an inventory of every payload Mach-O. The bootstrap is verified separately as the outer trust root; its exclusion from the payload inventory is not an exemption from signature validation. This policy never falls back to development policy.

Developer ID code requirements must constrain the Apple-issued Developer ID Application certificate chain, the expected Team ID and the fixed identifier. The verifier must validate signatures and resources with strict, all-architecture checks and validate nested code explicitly. Requirements come from trusted code or private owner configuration, never arbitrary requirement strings in the payload. Apple's [requirement-language reference](https://developer.apple.com/library/archive/documentation/Security/Conceptual/CodeSigningGuide/RequirementLang/RequirementLang.html) describes the certificate and identifier constraints.

Receipts and retained authorization evidence must bind a versioned authorization format, an immutable canonical trusted-policy digest and the authenticated manifest SHA-256. The policy digest covers its format version, pinned Team ID, component identifiers, requirement templates and native-inventory rules; a human-readable policy name alone is insufficient. Selection, launch, upgrade and rollback must compare that exact binding. Changing an owner-configured policy under the same name cannot silently authorize an existing release. A development receipt cannot replace a production receipt. Existing development and legacy records remain readable for their stopped migration operations, but are not implicitly eligible production rollback targets. File restoration continues to report runtime compatibility separately.

This policy protects distribution authenticity and accidental or external artifact replacement. It does not claim to defend against an attacker already able to rewrite all state and executables as the owning macOS user.

## Node and nested code

The inspected official Node 24.21.0 arm64 archive is checksum-verified, but its signed executable includes `get-task-allow=true`. Its upstream [entitlement file](https://github.com/nodejs/node/blob/v24.21.0/tools/osx-entitlements.plist) also includes several runtime exceptions. The copied executable therefore needs an explicit Ellie signing policy; retaining every upstream entitlement is not a suitable default for public distribution.

The first runtime experiment uses an owned copy with ad-hoc hardened signing and exactly `allow-jit` and `allow-unsigned-executable-memory`. Tests must exercise actual V8, workers, crypto and loopback TLS behavior. Broader exceptions require a reproduced failure and a reviewed justification. Ad-hoc success does not establish Developer ID library-validation behavior or notarization acceptance.

The builder must inventory native code by file bytes, not filename extensions, reject undeclared native code and sign nested code before its host. The current service dependency closure is JavaScript; future native add-ons must be reviewed and included explicitly. Production signing must remove debugging authority, use a secure timestamp and apply only the reviewed executable entitlements. The final product still requires Apple's [notarization and distribution checks](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution).

## Reviewable implementation sequence

1. Validate the narrowed Node entitlement set with a finite, isolated harness. Keep the production builder unchanged until the result is reviewed.
2. Add the authenticated-manifest verifier and sealed authorization-bundle layout with tests for changed resources, substituted manifests, incorrect publisher policy and untrusted native components. Keep production mutation unavailable until the receipt and launch binding is implemented; never expose a partially trusted install path.
3. Bind installed receipts, selection, recovery and launch to the verified policy. Preserve the existing stopped development migration contract and reject downgrade or mismatched recovery evidence.
4. Connect the production builder to an explicit private Developer ID identity, sign inside out, verify every component and create the sealed bootstrap. Refuse missing identity or incomplete native-code inventory; never silently substitute ad-hoc signing.
5. With the owner's signing credentials and an isolated logged-in macOS context, notarize and staple the final artifact, verify its publisher and Gatekeeper behavior, then exercise installed identity/Keychain/Accessibility continuity, lifecycle recovery and one explicit cross-Mac action.

PR75's finite ad-hoc runtime experiment and PR76's read-only authenticated envelope are incorporated into PR59 at `a068cff`. [PR81](https://github.com/rdimascio/ellie/pull/81), `da32f34`, publishes the full read-only manifest-v2 payload inspector after coordinating and independent review; its complete local gate passed 307 tests with one skip. It verifies inventory and native policy but cannot authorize installation. [PR77](https://github.com/rdimascio/ellie/pull/77) still awaits physical Developer ID runtime acceptance and the owner's already-requested Keychain unlock. Native CI failures and focused follow-ups are recorded in the [current checkpoint](validation/2026-09-14-release-trust-and-ci.md). Production owned capture, receipt/launch binding, signing and installed acceptance remain outstanding. No Team ID or signing credential is checked into the public repository.

## Next implementation contract: authenticated payload inspection

Implemented for review in PR81; the following contract remains the reference for that boundary. Paths in the table are release-relative locations. Manifest `nativeCode.path`, `machOPaths` and `files.path` are relative to `payload/`, so the Node record uses `bin/node`.

The next separately reviewable command is `inspect-authenticated-payload RELEASE AUTHORIZATION_APP --publisher-team-id TEAMID`. It must return an `AuthenticatedPayloadInspection` containing copied identifiers and digests, with no conversion to `SelectionRelease` or access to staging/selection mutations. It authenticates the envelope first, verifies the full payload inventory against the copied authenticated manifest and source bytes, and then checks native code. Its output explicitly states that installation and receipt binding have not been performed.

Use manifest v2 for this production inspection policy. Existing v1 development fields and operations retain their exact semantics; never reinterpret `development-ad-hoc` as production. V2 requires exact `developer-id` helper/launcher signature fields and a closed ordered `nativeCode` inventory. Team IDs and arbitrary requirement strings in the candidate confer no authority. The following fixed paths and identifiers come from the current builder, with a new stable identifier for the re-signed Node runtime:

| Path                                      | Kind       | Fixed identifier                      | Required native bytes         |
| ----------------------------------------- | ---------- | ------------------------------------- | ----------------------------- |
| `payload/bin/node`                        | executable | `org.ellie.runtime.node`              | this path                     |
| `payload/bin/ellie-service-installer`     | executable | `org.ellie.installer`                 | this path                     |
| `payload/helpers/ellie-macos`             | executable | `org.ellie.helper`                    | this path                     |
| `payload/launchers/Ellie Coordinator.app` | bundle     | `org.ellie.assistant.coordinator.app` | `Contents/MacOS/EllieService` |
| `payload/launchers/Ellie Node.app`        | bundle     | `org.ellie.assistant.node.app`        | `Contents/MacOS/EllieService` |

Each candidate native record has exactly `path`, `kind`, `identifier`, `machOPaths` and `entitlements`, and must equal the corresponding trusted record in the order above. Strings must be bounded ASCII for their complete value; arrays must have bounded lengths and unique entries, with no missing or additional keys and no type coercion. Executable `machOPaths` must equal `[path]`; bundle values are the single full payload-relative main-executable path. `entitlements` is a closed JSON object of boolean values. Node must equal `{ "com.apple.security.cs.allow-jit": true, "com.apple.security.cs.allow-unsigned-executable-memory": true }`; every other record must equal `{}`. These two runtime exceptions have only passed the ad-hoc experiment so far; successful Developer ID runtime acceptance remains pending. The authorization app is verified separately outside the payload inventory. Installed Applications copies are later transaction outputs whose bytes must match the authenticated launchers.

Every manifest file must be classified by bytes, independent of extension or mode. Detect thin and fat Mach-O in both byte orders, validate bounded headers/load commands/fat slices, reject malformed native-looking content, and require exact correspondence to the fixed native paths. This first policy accepts the single manifest-target CPU and rejects duplicate CPU records, so fat support is restricted to one target slice; it does not accept conventional multi-CPU universal payloads. Validate every bundle and each leaf or nested executable explicitly with strict all-architecture checks, the full fixed Developer ID requirement and the independently supplied Team ID. Each launcher's main executable must satisfy the same fixed role identifier and requirement as its enclosing app; encode that association explicitly in the trusted policy. Validate signing metadata and exact entitlement values only after signature validity; actual entitlement values must have CFBoolean type, since Foundation permits numeric 1 to cast to Bool. JS, resources, signatures and license files remain covered by the exact manifest inventory. New native addons, dylibs, frameworks or nested executables require an explicit policy/version change; none is currently included by the payload builder.

A separate canonical `PayloadInspectionPolicyV1` digest must bind a closed field schema and version, manifest version, envelope policy digest, exact native records, entitlements, full generated requirements and nested identifier associations, exact supported native magic values and numeric parser bounds, SHA-256, named strict all-architecture and explicit nested-code validation modes, and scope `authenticated-payload-inspection`. A digest binds these canonical data values, not arbitrary parser code semantics; a change to trusted validation semantics requires a policy-version change. Do not imply that PR76's envelope policy digest covers these additional payload rules. The result carries the envelope policy digest, payload policy digest and authenticated manifest hash separately; later authorization receipts must bind all three plus authorization version atomically.

Reuse the existing closed manifest grammar, owner/no-follow/link/mode/size/hash checks and exact bounded directory topology through narrow read-only helpers. Require byte equality with PR76's copied authenticated data and final release-root identity checks. This inspection result is not an atomic snapshot against a concurrent attacker with the same owner credentials; installation still requires an owned capture and revalidation transaction before mutation. Meaningful negative fixtures must cover envelope/payload substitution, file and topology changes, undeclared thin/fat native files, malformed headers, wrong publisher/identifier/entitlements, altered nested code and final root substitution. Test-only ad-hoc publisher relaxation must preserve every other check and remain absent from the shipping binary.

## Proposed next boundary: owned authenticated candidate capture

The next useful distribution slice should capture and revalidate an entire candidate, including its authorization app, rather than add another digest-only inspection wrapper. This proposal requires independent contract review before implementation.

Use a separate `authenticated-candidates` namespace beneath the existing `~/Library/Application Support/Ellie/Services` root. Preserve `~/.ellie` identities. A candidate contains the manifest-v2 release, the exact closed authorization-app layout and canonical binding metadata. It must never appear under selectable `releases`, and must not write receipts, role apps, LaunchAgents, selection journals or live state.

The transaction should copy through bounded descriptor-based primitives into its own private hidden stage, convert only captured modes, and fully verify the copied envelope and payload. Binding metadata includes version, scope, release ID, independently supplied publisher policy, authorization-record digest, envelope-policy digest, payload-policy digest and manifest digest. Reopen and revalidate the captured topology, all signatures and canonical binding bytes before exclusive publication. Define directory/file synchronization, post-publication sealing and failure outcomes explicitly. A competing candidate is accepted only after complete revalidation; uncertain cleanup or publication retains evidence. Neither a receipt nor launch authority follows from capture.

The existing inspector currently checks external `0644/0755` layouts. Captured `0444/0555` verification needs an explicit trusted mode policy, preserving external inspection semantics and authenticating copied bytes again. Candidate binding metadata must be derived from that captured verification, never trusted from the supplied source. The exact old/new binding schema, authorization layout, resource bounds and crash-recovery states need review against the current code before a writer begins.

Tests must cover changed sources during copying, substituted authorization evidence, every binding field, mode/topology errors, valid/invalid competing publications, failures before and after rename, incomplete cleanup and rejection by all existing selection/lifecycle/launch consumers. A later cohesive activation change must bind receipt v2, journals, recovery and launcher verification before any production candidate can be selected. Development manifest/receipt v1 must not silently upgrade, downgrade or inherit missing production evidence.

Independent contract review identified the following requirements to resolve explicitly in the implementation plan:

- Candidate identity derives from the full authority tuple: authorization version, publisher Team ID and trusted requirement policy, authorization-record digest, envelope and payload policies, manifest digest and source digest. Release ID alone is insufficient. Binding metadata is locally derived evidence; later use recomputes it through full signature and inventory verification.
- Define the entire captured release and authorization-app mode table: published roots/directories `0555`, data `0444`, executables `0555`, with every authorization child enumerated. Rerun signature checks after mode conversion. V1's installed-mode flag must not silently define V2 policy.
- Preserve the macOS 15 publication contract: namespace `0700`, hidden UUID stage root `0700`, sealed children, durable binding, stage/namespace synchronization, exclusive rename while the root is still writable, then root `0555` and root/namespace synchronization. A final `0700` entry is recoverable only after complete revalidation. Bound namespace count/bytes and define explicit retained-stage inspection/recovery; unknown or uncertain content must not be recursively removed.
- Use capture-specific locking/journaling inside `authenticated-candidates`, never `selection.lock`, whose presence without receipts can put current lifecycle into recovery-required state. Test that current stage, selection, lifecycle and migration remain unaffected and cannot interpret candidates as releases.
- Before success and on a competing destination, reopen the canonical Services-to-candidate chain, compare ancestor/device/inode identity, and fully revalidate topology, modes, hashes, signatures and canonical binding bytes. Later activation must revalidate its own captured source and bind receipt/recovery/launcher behavior together.
