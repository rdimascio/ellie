# Life core

`@ellie/life-core` is Ellie's local durable store for private and explicitly shared life data. The service supplies a trusted `{ userId }`; callers cannot claim group membership in an operation. The database owns group membership, resource scopes, records, settings, source chunks, relationships, and provenance.

Records use a generic JSON `data` object and one of the supported kinds: memory, contact, place, reminder, timer, event, birthday, holiday, need, goal, routine, source, or feedback. Titles, bodies, identifiers, nesting, arrays, and serialized JSON are bounded. Reminder and event clients can store `dueAt` as epoch milliseconds, `timeZone` as an IANA identifier, and `completed` as a boolean. Updates require the revision returned by the preceding read and throw `LifeConflictError` after a concurrent change.

`listRecordSummaries` provides a stable `(updatedAt,id)` cursor within one authorized scope and reports `hasMore` explicitly. It selects only a 240-character title/body preview and bounded primitive UI fields; full bodies, arbitrary data, relationships, and provenance remain available through `getRecord`. Summaries expose relationship count, whether any linked record is complete, and a valid/needs-review provenance status without copying those arrays into polling responses. Cursors are bound to the scope and kind filter and cannot be reused under another query.

Scopes are either `{ type: "user", id: userId }` or `{ type: "group", id: groupId }`. A user can only create or read their own private records. Group members can read and write group records; owners manage membership and group settings. Removing a membership immediately removes access. `personalSummary` and generation-bound `exportPersonalPage` provide bounded private records, complete source text, provenance, and raw user settings without group content. `deletePersonal({preserveMemberships:true})` supports the application reset workflow: it removes private records, chunks, feedback, guidance, and user settings while retaining group memberships and every shared record.

Group names are revisioned and owner-renamable, and one actor may own at most 32 groups. Existing identifiers and data survive the schema migration. A conversation may also hold actor-private `tone` (`calm`, `warm`, `playful`, or `direct`) and `verbosity` (`brief`, `balanced`, or `detailed`) overrides. Preference updates bind to an actor-owned pending turn, request ID, chat epoch, scoped fingerprint, and preference revision. They survive restart, appear in personal export, cascade with conversation deletion, and are removed by personal reset. A group-scoped conversation never shares these overrides with another group member.

Personal record and setting writes increment a durable per-user generation. Export cursors bind both that generation and the user identity. Pages target six MB and stop before adding another item; a single record is returned whole and can reach the store's bounded five-million-character body limit. A reset journal records the reviewed life/task/plugin generations and each completed deletion phase. It contains only a hash of the short-lived review token, and phases cannot move backward or skip ahead. This lets the application reject stale review, freeze other stores first, and safely retry an explicitly authorized reset after interruption.

Conversations are durable and private to the trusted actor even when their context is a group. `beginConversationTurn` requires the actor’s current `chatEpoch`, a stable request ID, the exact scope, and the original message. A duplicate retained request returns its authoritative pending, completed, or interrupted state without running work again. Restart changes pending turns to interrupted. Each actor may retain 100 conversations, each conversation 200 turns, each message 8,000 characters, and aggregate transcript storage is conservatively admitted under a 20 MiB quota. Paging is capped at 50 conversations or 100 newest-first turns.

Deleting a conversation keeps payload-free hashes of its request IDs for the current epoch, so deletion cannot turn an old HTTP retry into new effects. A personal reset increments the durable chat epoch and removes every actor-owned transcript, including those associated with a group the actor can no longer access. An old page carrying the prior epoch receives a conflict. Personal export includes only transcript contexts the actor can still access; it never exports shared group data merely because a private conversation referred to it.

A conversation can have one current durable life intent. The intent contains only an allowlisted reminder or event payload, missing `when` or `start` fields, its direct origin turn and request, exact actor-owned conversation scope, chat epoch, record-context fingerprint, revision, and 24-hour expiry. A continuation can fill only the declared temporal field through a new actor-owned pending turn. It cannot supply an actor, scope, handler, capability, record identifier, or arbitrary record data. Repeating creation for the same origin is idempotent. A current-pointer table prevents an older expired or interrupted draft from resurfacing after a newer draft completes or is cancelled. Awaiting drafts survive restart; executing drafts become interrupted and are never replayed automatically. Conversation deletion cascades an inert draft but refuses an executing one. Export includes only currently accessible context; reset deletes all actor drafts, including revoked contexts.

A correction such as “Actually make it 11” is authorized only by that current direct message and a validated receipt from the immediately preceding completed operation. The receipt stores the exact record kind, ID, and revision; any intervening edit makes it unusable. Reminder rescheduling uses a durable actor-linked journal plus TaskRuntime’s prepared replacement: the old and replacement tasks remain nondispatchable until the record revision and new task pointer are durable, then activation cancels the old task and schedules the new one. Startup recovers these phases before the scheduler starts. Personal reset refuses to discard an unresolved actor-linked shared journal.

Completed turns store bounded action labels and evidence references for display. Model history uses only the most recent completed turns whose compact record/settings fingerprint and exact cited source revisions are current. Settings values are part of the fingerprint, so two changes at the same timestamp still invalidate history. Stale turns remain visible as history but are not restored into model context. Evidence freshness reads source metadata only and never loads a large source body.

Settings resolve in default, active group, user, then task order and return an origin for every effective key. Values can be any bounded JSON value. Keys related to permission, authority, authentication, capabilities, roles, or membership are rejected at every setting level; permission remains a separate authority.

Text, Markdown, HTML, email, and transcript sources are normalized into bounded chunks. Metadata is generic JSON and should include `filename` and `mimeType` when known. Binary formats use `BinaryExtractor`, keeping parser dependencies outside this package. Search is lexical, bounded, cited by source and chunk, and filters authorized scopes before scoring. Source content is inert data: HTML scripts are removed during normalization, and records mark source content as untrusted. Updating or deleting a source replaces/removes its chunks and adds `invalidatedAt` to provenance entries in derived records. Clients can present a memory as valid when no provenance entry is invalidated and as needing review otherwise.

`commitImport` validates an entire calendar or contact import before opening one transaction. It writes the inert source, normalized chunks, selected records, relationships, and scoped provenance together. Source hashes and item keys derive stable identities, so repeating an import is idempotent. Imported records carry their managed revision; a later import preserves and reports any record the user edited instead of overwriting it.

`updateNotification` dismisses a notification with a required revision. Its `complete` action also marks a linked reminder, need, or goal complete in the same transaction. `createProactiveNotification` atomically checks the source record revision and cooldown while creating the notification and updating its delivery marker.

`recordFeedback` always retains an inspectable feedback record. It changes a lasting setting only when `explicitPreference` is present. Callers explicitly choose personal or group preference level; group level still requires owner authority. `inferTone` returns a temporary signal and writes nothing.

The schema has no encryption layer or semantic/vector search. SQLite file and directory access is limited to the current OS user through ownership, mode, symlink, and hard-link checks. Backup encryption and at-rest key management belong to the service deployment design.
