# Life service

Ellie Life is a separate, explicitly started local application. It does not start or modify the existing Ellie coordinator, services, household data, `~/.ellie`, or Keychain. Its default state is `~/.ellie-life`; tests and embedded callers should pass a dedicated private directory. The launcher rejects state inside the source checkout, canonicalizes the nearest existing ancestor before creating anything, and requires the resulting directory to be owned by the current user with mode `0700`. The life, task, and plugin databases enforce their own regular-file, ownership, link, mode, integrity, and schema checks.

Start it with Node 24:

```sh
node apps/life/src/main.ts --state-dir /private/path/to/life-state --port 7440
```

The state directory is optional and defaults to `~/.ellie-life`. Port `0` selects an ephemeral port for tests. A local OpenAI-compatible model is optional and requires both `--model-url http://127.0.0.1:PORT/` and `--model NAME`; non-loopback, authenticated, and non-HTTP model URLs are rejected before stores are opened. `runLife(args)` is available for root CLI dispatch. `createLifeApplication(options)` assembles `LifeStore`, `TaskRuntime`, `PluginStore`, local document extraction, the life harness, and the HTTP service, and exposes idempotent `listen()` and `close()` methods.

On readiness the launcher prints one URL containing a cryptographic token in its fragment. Fragments do not travel in HTTP requests. The UI removes the fragment and sends the token once to `POST /api/life/session`. The launch token expires after ten minutes and cannot be reused. A successful exchange issues a random opaque cookie with `HttpOnly`, `SameSite=Strict`, `Path=/`, and a twelve-hour lifetime. The cookie omits `Secure` because this first listener is local plain HTTP. Only hashes of launch and session tokens are retained by the server. Session attempts are rate limited.

The listener binds only `127.0.0.1` and validates the exact bound `Host` value. Every non-GET/HEAD request requires the exact local `Origin`. There is no CORS response. Every `/api/life/*` route except session exchange requires the session cookie. Responses use `nosniff`, `Referrer-Policy: no-referrer`, bounded request sizes and deadlines, and do not log request bodies or raw errors. Ordinary JSON is limited to 128 KiB; source requests are limited to 2 MiB. Writes require `application/json`.

Shutdown stops new admission, closes listener sockets, aborts service-owned extraction, and waits up to five seconds for active handlers. If model-backed or other work remains unsettled, close reports that condition and the application keeps its stores open; callers can retry after the handler settles. This prevents late handlers from using a database that shutdown already closed.

The authenticated API is:

- `GET /api/life/bootstrap?scope=user:local|group:ID` returns the profile, authorized groups, the first 100 compact World summaries plus `recordsPage`, and a separately filtered `agendaRecords`/`agendaPage` for reminders, timers, events, birthdays, and holidays. Notifications are also queried independently from event/feedback records, so a large source corpus cannot hide an older commitment or notification. Further agenda rows use `/records` with the exact timed-kind filter and returned cursor. Bootstrap also returns tasks, resolved settings as `{ values, origins }`, truthful reminder notification fields, and plugins. The profile time zone is the effective scoped setting. Arcade summaries include that user's high score. MLB summaries include a snapshot or an explicit unavailable/stale result. Group membership is rechecked after awaited provider reads before any snapshot is returned.
- `GET /api/life/groups` lists authorized local shared spaces with role and revision. `POST /api/life/groups` accepts only `{name}` and generates its identifier. `PATCH /api/life/groups/:id` accepts `{name,expectedRevision}` and requires owner access. There is no invitation, membership, or group-deletion HTTP route.
- `GET /api/life/records?scope=...&limit=...&cursor=...&kinds=...` pages compact summaries, while `GET /api/life/records/:id` lazily returns one full authorized record. `GET /api/life/search?scope=...&q=...&limit=...` returns bounded source chunks with citations. `POST /api/life/records`, `PATCH /api/life/records/:id`, and `DELETE /api/life/records/:id?revision=N` provide record CRUD. Patches use `expectedRevision`; `revision` remains a compatibility alias. Successful edits and deletion invalidate the matching conversation context.
- `POST /api/life/sources` imports text, Markdown, HTML, email, and transcripts. Binary content uses base64 plus the injected local extractor. Unsupported formats return an explicit error rather than pretending ingestion succeeded.
- `POST /api/life/sources/binary?scope=...&filename=...&mimeType=...&title=...` accepts a raw `application/octet-stream` body for PDF, image, and other configured local extractors. It requires an exact `Content-Length`, caps input at 50,000,000 bytes, limits the service to two simultaneous binary uploads, and enforces a 60-second upload/extraction deadline. Extracted text is capped at five million characters. Reset and shutdown abort extraction, and group access is checked again after extraction before anything is stored. The `201` receipt omits the full extracted body and returns only a 240-character preview; clients retrieve full text lazily through record detail. The existing JSON route remains available for small compatibility uploads; its two-MiB request limit is unchanged.
- `POST /api/life/import/preview` parses original ICS or vCard content into reviewable items and warnings without persisting it. `POST /api/life/import/commit` resubmits and reparses that original content with optional selected keys; client-supplied preview objects are ignored. Deterministic identities make repeats idempotent, while records edited after an earlier import are preserved and reported as conflicts.
- `POST /api/life/settings` applies a whole default, user, or owner-authorized group settings batch atomically. Authority-related keys remain forbidden.
- `POST /api/life/feedback` records inspectable feedback and accepts the richer learning fields for compatibility. An explicit preference remains personal by default even in group chat; `sharedSetting:true` is required to request an owner-authorized group setting. Chat-response feedback includes an owned `conversationId` and completed `turnId`; the service replaces client prompt/response text with that authoritative turn and stores the example in the actor’s private scope. Deliberate learning without a conversation binding retains its explicitly requested scope. `POST /api/life/learning` records a rating or correction; `GET /api/life/learning?scope=...` lists scoped history; `POST /api/life/learning/:id/selection` revision-selects a personal example; and `POST /api/life/learning/export` returns an explicit, local `{ format, count, jsonl }` export. Group examples and unselected personal examples cannot be exported. `POST /api/life/chat` requires `{scope,message,requestId,chatEpoch,conversationId?}`. The service persists the user turn before invoking the harness, supplies only trusted current history and conversation preferences, and completes the turn and any preference update atomically. Repeating the identical request returns the stored status and never reruns effects; a changed payload with the same request ID is a conflict. Chat responses and conversation detail always include `conversationPreferences:{preferences,revision}`; empty is `{preferences:{},revision:0}` and cleared keys are absent. HTTP callers cannot inject trusted overrides. An unqualified group-chat style request stays actor-private; shared settings require explicit shared-setting intent and owner authority. `GET /api/life/chat/requests/:requestId` recovers a request after a disconnected response. `GET /api/life/conversations?scope=...` returns the current chat epoch and a stable page of private conversation summaries; `GET /api/life/conversations/:id` returns newest-first turn pages; `DELETE /api/life/conversations/:id?revision=N` rejects pending work and retains replay protection. Group access is rechecked for every read even though the transcript itself belongs only to the actor. `GET /api/life/model/status` reports deterministic or configured local-model readiness without probing during bootstrap.
- Missing-time reminders and events use a durable trusted continuation. “Remind me to call Mum” returns a `pendingIntent` strip with its kind, title, missing field, revision, and 24-hour expiry. The next ordinary `POST /api/life/chat` may fill only that missing time; the HTTP body never accepts a structured intent. Every chat response, including duplicate and request recovery, recomputes `pendingIntent` as an object or explicit `null`. `GET /api/life/conversations/:id/pending-intent` restores the strip after reload. `DELETE` on that route with `?revision=N` clears an awaiting draft. Conversation deletion also clears an awaiting draft but rejects executing work. A direct immediate correction uses the preceding stored operation receipt and revision; it cannot infer a target from transcript prose.
- Reminder correction prepares a nondispatchable replacement task, revisions the exact reminder to point at it, then activates the replacement and cancels the old task. A durable life journal records each boundary. The server reconciles journals during construction, before the application starts TaskRuntime. Reset first settles actor-linked journals, including group-owned tasks; an inaccessible shared journal blocks reset instead of orphaning paused shared work.
- `POST /api/life/signals` evaluates one explicit, scoped shopping, location, price, or preparation-check observation. Location coordinates are used for the immediate match and are not retained. The resulting notification record stores the reason and related record, while reported prices remain attributed to the caller-supplied source.
- `POST /api/life/notifications/:id/dismiss` and `POST /api/life/notifications/:id/complete` require `expectedRevision`. Completion atomically closes an authorized linked reminder or need, then cancels matching pending delivery work. Dismissal and completion remove the notification from subsequent bootstrap responses.
- `POST /api/life/tasks/:id/pause|resume|cancel|run` first finds the task under the user's authorized owner scopes, then performs the transition using that stored owner. Task summaries include the currently valid action list. Running a terminal source-aggregate task creates and returns a new root workflow against current source revisions while retaining the old task as immutable history; other terminal tasks return conflict.
- `GET /api/life/tasks/:id/detail` returns the task summary, at most 100 recent progress entries, and at most 500 child state summaries without task input. A persisted aggregate source summary is returned only while every citation remains readable in the exact task scope at the exact source revision; otherwise the response marks it stale and withholds the aggregate prose.
- `POST /api/life/plugins/build` installs a built-in arcade or MLB plugin, or uses the optional model-backed builder. It returns unavailable when custom generation is not configured.
- `GET /api/life/plugins/:id/view` serves only a plugin found by enumerating authorized owner scopes. `POST /api/life/plugins/:id/action` permits only declared `storage.get`, `storage.set`, or `mlb.snapshot` grants. Group plugin storage uses an unambiguous base64url-encoded active-user namespace, so user IDs containing colons cannot collide with another user's key.
- Custom plugin documents receive a synchronous, immutable `window.ellie` SDK before plugin markup runs. Version 1 exposes `ellie.storage.get(key)` and `ellie.storage.set(key, value)` promises. Values are canonical JSON up to 16 KiB, keys use the same 512-character host grammar, storage calls time out after five seconds, and each page may hold at most 32 requests. The opaque child owns the host port; custom code receives only a separate legacy-compatible local port. Legacy MLB reads have a 15-second deadline. Page teardown rejects outstanding SDK calls.
- `POST /api/life/plugins/:id/revise`, `POST /api/life/plugins/:id/rollback`, and `DELETE /api/life/plugins/:id` expose scoped version changes, rollback, and removal. Revision preserves existing grants; it cannot acquire capabilities.
- `GET /api/life/plugins/:id/history` returns up to 100 retained revision summaries without generated HTML. Plugin lookup uses the stored authorized owner before history or mutation.
- `GET /api/life/teaching?scope=...` and `GET /api/life/teaching/:id` return versioned adopted guidance. `POST /api/life/teaching` creates a guide; `POST /api/life/teaching/:id/revise|enabled|rollback` require the current record revision. Source revisions are rechecked by `LifeTeaching`, and successful changes invalidate conversation context. Generic record-body editing is not used for these controls.
- `GET /api/life/personal-data/review` returns concrete private life/task/plugin counts, byte estimates, three store generations, and a single-use ten-minute review token. `GET /api/life/personal-data/export?reviewToken=...&store=life|tasks|plugins&cursor=...&limit=...` pages each store independently with at most 100 items. Every page checks a cheap per-user generation counter, so unchanged exports do not rescan source bodies merely to validate consistency. It includes full private source text, task history, owned plugin manifests and versions, owned storage, and only the active user's encoded storage in shared apps. It contains no shared records, tasks, app manifests, or another user's storage. A mutation between pages invalidates the cursor and requires a fresh review; the three stores are separately generation-bound rather than represented as one cross-database transaction.
- `POST /api/life/personal-data/reset` is the only operation that commits a reviewed reset. It freezes personal task admission, aborts and drains active personal work, then deletes user-owned tasks, apps, storage, private life records, guidance, feedback, user settings, and all actor-owned conversations, including revoked-scope transcripts. It also advances the chat epoch so an old request cannot replay after reset. It preserves group memberships and all shared records/apps/tasks. The response is `200` when complete or `202` with an operation ID while draining. `GET /api/life/personal-data/reset/:operationId` reports the durable phase; `POST .../:operationId/retry` resumes an interrupted, previously authorized operation without requiring a now-expired review token. Other writes return `423` while a reset is incomplete.

The service never accepts an HTTP user ID or capability list. Its trusted actor defaults to `local`; tests and embedding code can inject another stable user ID. User and group scopes are checked against `LifeStore` membership, while record, task, and plugin mutations resolve the stored owner before acting.

Static UI files contain no personal state. A plugin view first loads a trusted service-owned host document. That host creates a nested `sandbox=allow-scripts` frame for the untrusted plugin and brokers one child-only message port; navigating or reloading the child closes the bridge. Its inherited CSP denies default access, network, forms, objects, and base URLs, allows inline scripts/styles and data images, and permits framing only by the same-origin Ellie UI. Plugin code is served to the browser and is never executed by the server.

Current limitations are local HTTP, in-memory sessions, a single local trusted actor per process, and no remote access. Restarting the service requires a new launch-token exchange. At-rest encryption and HTTPS require a later deployment design; the current implementation relies on OS-user file isolation and loopback-only transport.
