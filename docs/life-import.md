# Calendar and contact import

`@ellie/life-import` parses calendar (`.ics`) and contact (`.vcf`/vCard) text as inert data. Import has two explicit phases. `previewLifeImport` returns a bounded JSON preview with stable item keys and visible warnings and performs no writes. `commitLifeImport` accepts the original content and selected preview keys, reparses it server-side, and asks `LifeStore.commitImport` to validate and atomically store the source and selected records. A client-modified preview object is never accepted as record authority.

ICS previews support `VEVENT`, folded lines, escaped text, UID, summary, description, categories, all-day `VALUE=DATE`, UTC date-times, and date-times using a valid IANA `TZID`. A floating date-time needs an explicit default time zone. Zoned timestamps are matched through the shared exact date, hour, minute, and second calendar primitive, including half-hour DST transitions. Unknown time zones, nonexistent or ambiguous DST wall times, malformed dates, recurrence rules, and recurrence exceptions stay visible as warnings; the importer does not invent an offset or expand/schedule recurrence. Imported components never create background tasks or execute text from descriptions.

vCard previews support `FN`, `UID`, `EMAIL`, `TEL`, and `BDAY`. A birthday may omit its year, and February 29 remains valid. A birthday item links to its contact through a stable preview key, which the atomic store resolves only among the validated selected records.

Content is limited to 2 MB, 20,000 physical lines, and 2,000 components. Titles, fields, selections, and warning output are bounded. Remote URLs are not fetched. Attachments, alarms, contact photos, arbitrary vCard extensions, VTIMEZONE definitions, attendee updates, and calendar recurrence expansion are outside this initial parser.

The content SHA-256 identifies a newly imported source in its scope, so uploading the same file again is idempotent. Supplying an existing source ID is an explicit source update. Item IDs derive from that stable source ID and the UID-based item key. Imported records retain the source and item key, fingerprint, managed revision, and provenance reference. Reimport updates only records still at their importer-managed revision; a user-edited record is preserved and returned as a conflict warning. Source and item validation completes before one transaction writes anything. Deleting the source uses `LifeStore.deleteSource`, which removes indexed content and invalidates dependent provenance according to the core retention rules.
